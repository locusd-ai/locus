Locus/ˈloʊkəs/ · the set of all points satisfying a condition

Your agent greps, guesses, and dumps whole files into its context. Locus hands it pointers instead.

Index your code and notes once. Ask a structural question, get back the exact file, symbol, and byte range — plus why it matched. The agent reads only what it picks. Nothing leaves your machine.

Context is the budget72 documents

Ask an agent “where is database access implemented?” It greps, gets nineteen hits, and reads all nineteen files: 80,824 tokens spent to find out where to look. Locus answers the same question with a 20,940-token digest of labelled pointers. Do this eight times in a session and the difference stops being a rounding error — the window goes to rediscovery instead of reasoning.

Across eight such questions, answered from an index Locus already built — same corpus, same questions, three strategies:

Eight “where is…?” questions over this repository’s crates/ — 72 documents, 1,099 chunks. Tokens approximated as bytes ÷ 4. Reproduce with scripts/token-bench.py.

Seven times fewer, and the digest is often the whole answer — file, symbol and range are usually enough to know where to look. When content is genuinely needed, the agent reads the ranges it chose.

Some questions have no grep equivalent at all. complexity:high, visibility:public, convention:test, async:true — these aren’t strings in the file. They’re facts about the syntax tree, indexed at ingest.

Three stages,
cheapest first

How it resolvesbitmap → vector → graph

Each stage is more expensive than the last, so each one only ever sees what the stage before it kept.

  1. Bitmap pre-filter

    Every tag, folder, language, kind and convention is a Roaring bitmap over document IDs. topic:database AND folder:crates/locus-query is a handful of compressed bitwise ops — and it costs the same whether the corpus holds a thousand documents or a hundred thousand.

    16µs single key · 19µs AND · at 100,000 documents, in memory

  2. Semantic rerank

    Local ONNX embeddings and an HNSW index score only the candidates the bitmap kept. No GPU, no API key, no request leaving the machine. Vector search is linear in candidates, which is exactly why it runs second.

    ~25–55ms end to end, including query embedding

  3. Graph expansion

    Wikilinks, imports and references form a graph. locus graph expand pulls the n-hop neighbourhood of a result; locus graph central finds the documents everything else leans on.

    the load-bearing files, without reading any of them

The bitmap stage is the reason the rest is affordable. Compared against every alternative you’d reasonably reach for, on compound queries at 100,000 documents:

AND query, median of 100 runs, in-memory store — isolating lookup cost from build cost. On-disk LMDB reads cost ~9ms cold, converging toward the in-memory figure once the daemon has warmed the page cache. Full method in docs/benchmarks/REPORT.md.
ApproachAND queryPersists?
SQL (DuckDB)4,758µsyes
Property graph (petgraph)4,075µsno

A HashSet beats Locus on a single-key lookup — nothing beats a hash. But intersection walks elements, so it degrades as sets grow, and it forgets everything when the process exits. Roaring intersects compressed blocks at a cost that barely moves, and the index is still there tomorrow.

What it indexes6 sources

  • Markdown & Obsidian vaultsfrontmatter · tags · wikilinks · sections
  • Code, via tree-sitterRust · TypeScript · Python
  • Confluencespace · label · author
  • Jiraproject · status · assignee · sprint
  • Slackchannel · author · thread
  • Anything that can POST JSONwebhook ingest

Code parsing runs at ~9,500 files per second — roughly 75,000 AST chunks — and enrichment at ~66,000 files per second cold, ~325,000 warm. Re-indexing an unchanged vault is a blake3 hash and a map lookup, so it is essentially free. A notify-based watcher keeps the index live as you edit.

For the agent7 MCP tools

The locusd daemon speaks MCP, so the engine shows up as tools your agent can call directly:

  • locus_search
  • locus_semantic
  • locus_graph
  • locus_inspect
  • locus_filters
  • locus_status
  • locus_remote_ingest

locus_filters is the one that changes the dynamic: the agent asks what keys exist before it asks anything else. It stops guessing at your directory names and starts querying a map it can actually read.

Start here

Install~/.locus

$ git clone https://github.com/locusd-ai/locus && cd locus
$ cargo install --path crates/locus-cli
$ cargo install --path crates/locus-daemon

$ locus init ~/notes                  # markdown or Obsidian
$ locus init ~/code/myrepo --type code
$ locus index ~/code/myrepo

$ locus search "topic:database AND lang:rust"
$ locus semantic "how do we handle auth?"

$ locus mcp install ~/code/myrepo      # your agent now has a map

Three rules it doesn’t breakby design

  • §Local-first. The index lives in ~/.locus. No cloud, no telemetry, no API keys, no account.
  • §Pointers, never content. A query response cannot contain your file contents. That isn’t a setting — the response type has no field for it.
  • §Embedded-grade Rust. DuckDB registry, LMDB and Roaring bitmaps, usearch HNSW, tree-sitter parsing. Sync core; async only at the daemon edge.
